# RCA — 2026-10-28 — Simulated PostgreSQL outage (M9 incident simulation)

Template: [rca-template.md](./rca-template.md). This incident was deliberately injected
(`docker compose stop postgres`) to exercise the detection/response path, not a real production
event — all data is synthetic and this is a local docker-compose environment. Every timestamp
below is real, captured live during the simulation (not reconstructed afterward).

## 1. Summary

`mortgage-service` lost its database connection for ~32 seconds when PostgreSQL was stopped.
Every request requiring a database read or write during that window failed with `500
INTERNAL_ERROR`; health checks and already-issued JWTs were unaffected since neither touches the
database. Service recovered automatically within seconds of PostgreSQL restarting, with no
manual intervention beyond restarting PostgreSQL itself.

## 2. Impact

- **Affected:** `mortgage-service` (8080) write/read endpoints requiring PostgreSQL — login,
  mortgage/borrower/payment CRUD. `servicing-service` was not exercised in this simulation but
  shares the same database and would show the same failure mode.
- **Not affected:** `/actuator/health` (no DB dependency in the check itself — see "Preventive
  actions" below, this is actually a gap, not a feature), already-issued JWTs (stateless,
  validated against the shared secret, no DB lookup).
- **Duration:** ~32 seconds (database stopped 22:32:33Z, confirmed recovered 22:33:05Z).
- **SLO breach:** Payment API success rate SLO is 99.5%/30d (`docs/operations/slo.md`) — a
  32-second full outage is a small fraction of the 30-day error budget (~3.6 hours), well within
  budget on its own, but is exactly the kind of event that SLO tracking should accumulate.

## 4. Root cause

**Technical root cause:** `mortgage-service` holds a HikariCP connection pool to PostgreSQL.
When PostgreSQL stops, in-flight and new connection attempts fail; HikariCP's connection
timeout (3001ms, the default `connection-timeout` plus HikariCP's internal margin) means every
request needing a DB connection during the outage waits ~3 seconds before failing, rather than
failing instantly — each failed request was slower than a clean "service unavailable" response
would be.

**Contributing factors:**

1. The error envelope correctly returned a generic `INTERNAL_ERROR` (no stack trace, no
   connection string, no internal exception type) — this is the *security* control working
   correctly (`docs/security/vulnerability-report.md`), but it also means an on-call engineer
   looking only at the HTTP response, not the logs, can't distinguish "database down" from any
   other 500. The logs had the real cause immediately (`CannotCreateTransactionException`); the
   API response, by design, didn't.
2. **A separate bug, found while verifying this RCA's first draft:** `curl
   http://localhost:8080/actuator/health` correctly returned `503 {"status":"DOWN"}` during the
   outage (Spring Boot's default `DataSourceHealthIndicator` worked as expected) — but
   `/actuator/health/readiness` and `/actuator/health/liveness`, the Kubernetes-probe-group
   paths `management.endpoint.health.probes.enabled=true` exists specifically to serve, returned
   **401 Unauthorized** instead, with or without the outage. `SecurityConfig` in both Java
   services permitted the wrong paths — literal `/actuator/readiness` and `/actuator/liveness`
   — instead of the paths Spring Boot actually serves, nested under `/actuator/health/*`. This
   had been silently broken since M4 and would make a real Kubernetes deployment's readiness/
   liveness probes always fail authentication, not reflect this app's actual health. **Fixed in
   this same milestone** (both services now permit `/actuator/health/**`), verified live
   before/after the fix, and covered by a new regression test in each service
   (`AuthControllerTest`/`RbacTest`: `actuatorHealthProbeGroups_arePublic_withoutAToken`).

## 5. Corrective actions

None needed beyond restarting PostgreSQL — which is what resolved it, and is already documented
in `docs/operations/runbook.md`. No data was lost or corrupted: every request during the outage
either failed cleanly (500, no partial write — Spring's `@Transactional` ensures a connection
failure before the transaction starts means nothing was written) or succeeded normally once the
connection was restored.
